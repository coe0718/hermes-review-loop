# Issue #16: isolated route-to-agent boundary (offline vertical slice; NOT deployable)

The reviewer and fixer webhook scripts now always return `[SILENT]` before native gateway dispatch. Eligible events create a durable, deduplicated supervisor record and launch a detached worker **only if** a private runtime file exists at `$HERMES_HOME/review-loop-runtime.json`. Missing or invalid configuration fails closed; the old gate pending queue records the reason. No route returns a `FIRE` payload or falls back to the credential-owning gateway agent. The legacy adjudicator route remains silenced; a spent cap instead enqueues an isolated `adjudicator` turn (turn key `breach:<rounds>`) through the same supervisor, whose worker re-reads the live PR, reviews and breach marker before launch, mounts the exact-head export read-only, and whose broker accepts exactly one `ruling` (ACCEPT/REJECT/RESPEC + bounded reason). The host records the ruling in the run ledger before anything else, then sends an observer `ruling` notice and queues it in the operator outbox, and posts a PR issue comment only for an optional, distinct `seats.adjudicator.login` identity (distinct login, token file and `/user` principal, rechecked against the live PR before the POST). A comment whose POST outcome is unknown is recorded as `uncertain` and never retried.

The runtime file must be mode 0600 and name the host paths `source`, `venv`, `runtime` and `rust`. Each seat's model, provider and key come from **that seat's Hermes profile**, resolved host-side per turn by Hermes's own resolution in a separate process with a from-scratch environment (issue #32); an explicit `seats.<seat>` override, and the legacy top-level `model`/`upstream`/`key_file` as a fallback only for an unresolvable profile, are also accepted (precedence and supported providers: [configuration](configuration.md#runtime-file-and-seat-models-review-loop-runtimejson)). The upstream must be HTTPS and one of the proxy's per-`api_mode` contracts — `chat_completions`, `codex_responses` or `anthropic_messages` — each with a host-fixed upstream path, a fixed sandbox path, a request-header allowlist (sandbox `Authorization`/`x-api-key` always dropped), the body model forced to the seat's, the output cap enforced in that mode's own field, and quota. OAuth/subscription providers that resolve to one of those (`openai-codex`, `xai-oauth`, `qwen-oauth`, `nous`, `minimax-oauth`, a Claude subscription on `anthropic`) are accepted: only the short-lived access token reaches the proxy, and the host re-runs the isolated Hermes resolution near its expiry or once after an upstream 401 (serialized per profile, through Hermes's own `auth.lock`), so the refresh token never leaves the host's Hermes auth store. Copilot, Bedrock, Vertex, Azure Foundry, MoA, the `codex_app_server` runtime and any other `api_mode` are refused before their credentials are touched, and an unresolvable seat is held before launch with the reason in the ledger — never run with another seat's model or key. The worker verifies the current PR head before staging and starts a host-key-only inference proxy and a scoped Unix-socket broker. The bubblewrap process sees a bounded snapshot of hash-verified regular blobs from one pinned source commit (not dirty or staged worktree bytes), bounded exact-head checkout export, throwaway HOME, offline Rust toolchain, and the two socket directories. It does **not** receive the model key or OAuth token (the seat's `config.yaml` names only the model, the local bridge, the matching `api_mode` and a dummy key — for a Claude subscription a dummy OAuth-shaped `ANTHROPIC_TOKEN` so Hermes applies the Claude Code request identity), any profile's `.env`/`auth.json`/`auth.lock`/`config.yaml`/`.anthropic_oauth.json`, the user's Claude Code/Codex/Qwen credential files, GitHub PAT, host home, or arbitrary host network. One turn's proxy holds only its own seat's credential. The scoped broker supports review, review request, and a local exact-SHA-lease push; the PR-state checks immediately before and after a push are **not atomic** with a concurrent state change.

The SQLite ledger commits identity before launch, deduplicates `(repo, PR, head, seat)`, limits seat concurrency, leaves ambiguous launched jobs `uncertain` rather than retrying writes, and retries expired *pre-launch* claims. A run that failed with nothing on its write-ahead record (no receipt claim, push intent or ruling) waits with backoff and is relaunched a bounded number of times; a redelivered event or `hermes review-loop retry` re-arms a failed one (issue #53, [details](operations.md#when-an-isolated-run-fails)). A live worker heartbeats its lease; an expired worker is quarantined, never relaunched. A delayed completion from the same owner can still release its uncertain seat after its child stops. Failed and uncertain runs enter a durable operator notice outbox; each watchdog sweep emits up to 20 notices via its existing cron stdout delivery, independently of paused hooks or GitHub availability. Notices carry PR URL, seat, full head and stable run ID. A failed local delivery callback leaves the notice pending; repeated successful sweeps emit it once. Run `python -m review_loop.run_supervisor status $HERMES_HOME/state/review-loop-runs.sqlite` to inspect up to 100 failed/waiting/uncertain rows, their reason, output tail and notice state; `python -m review_loop.run_supervisor sweep DB` manually recovers expired leases and emits notices without launching workers. To release an uncertain seat, **first** establish no worker or descendants remain and inspect external GitHub writes, then use `python -m review_loop.run_supervisor reconcile DB RUN_ID --reason 'external writes inspected' --acknowledge-no-live-worker`. Present/inaccessible PIDs block release; PID absence alone is insufficient. Reconciliation marks the run failed, is idempotent, and never replays the original write. A later worker-enabled recovery may schedule *other* pending turns.

Cron stdout is only a local handoff, not a confirmed end-user receipt: a scheduler/transport failure after the ledger marks delivery can lose a notice; a crash after stdout but before committing delivery can duplicate it. The stable run ID supports downstream deduplication. Confirm the cron delivery target and inspect `status` regularly until an acknowledged transport exists; do not treat a `delivered` ledger flag as proof the user received it.

## Live verification: `hermes review-loop selftest`

`hermes review-loop selftest --loop ID [--pr N] [--no-model] [--live-turn] [--timeout S]` (see [Verifying the isolated setup](operations.md#verifying-the-isolated-setup-selftest) for the command order) checks, step by step, the private runtime file, bubblewrap user namespaces plus a probe in the configured sandbox layout that must not read a dummy host secret or any configured secret path, each seat's resolved profile → provider / model, one tiny real completion through `InferenceCapability` per distinct seat resolution, `/user` identities and distinct principals, the reviewer-write authorization (`broker.authorize`, GET only), the supervisor ledger and `doctor`'s cron/gateway checks, and optionally one real isolated reviewer turn.

No-write guarantees: every GitHub call during the selftest passes a GET-only guard around `gh.fetch`. The live turn's `RunBroker(..., no_write=True)` is a **host-only constructor flag**, accepted only for reviewer scopes and read-only afterwards. It is not a socket field: requests keep exactly `operation/verdict/body`, so a request carrying any extra key is refused. In that mode the broker serves one `review`, runs `broker.authorize` (reads only), records the verdict/body in host memory and answers the sandbox as a real write would. It never calls `broker.perform`, `review_receipt.submit`, the audit log or a ledger. The printed checklist is redacted against the configured PATs and model key.

What it does not prove: the live turn runs in the CLI process, not the detached supervisor worker (different environment, no ledger row, no operator notice), so alert delivery still has to be confirmed with a real enqueued turn and a watchdog sweep. It also does not close the blockers below.

## Remaining blockers before claiming #16 complete

1. The source-snapshot and local clone trust roots require a production security review, including symlinks, file races, `/proc`, mounted sockets and the installed runtime. The isolated agent shares the host UID inside a user namespace, not a separate host identity (`review_loop/trusted_turn.py`, `review_loop/contained.py`).
2. The broker requires a freshly read PR with `state == "open"`, `draft is False`, matching PR number/base/head repository/branch/SHA, and verified seat identities before every review/review-request POST and at the push's preconstruction and pre-push checkpoints. Missing or non-boolean draft status fails closed. The push additionally checks the scoped branch SHA before construction and immediately before its exact-SHA-lease Git push; after pushing it reads back the ref and PR and withholds acknowledgement if either is unverified. **This is not an atomic PR-state/ref compare-and-swap.** Git's lease only constrains `refs/heads/<branch>`. A close, draft conversion or retarget immediately after the last PR read can still occur before receive-pack accepts an unchanged branch ref. Even the final readback cannot prove there was no intervening ineligible state: `test_close_reopen_between_final_check_and_push_exposes_residual_race` models a close/reopen wholly within that window and the push is acknowledged. Persistent ineligibility at readback is reported as `published_pr_unverified`, but cannot undo the already published ref. A GitHub-side transactional guard (or a policy that accepts this risk) is needed before production writes (`review_loop/safe_push.py`).
3. Operator reconciliation and the local cron notice outbox are offline-tested, but end-to-end acknowledged user delivery and a live authenticated provider test remain unverified — including whether the ChatGPT Codex backend and the Claude subscription endpoint accept exactly the requests the sandboxed Hermes sends through a custom provider (verified only against fakes) (`review_loop/run_supervisor.py`). The integration fake models HTTPS transport via a test-only substitution, not an authenticated TLS provider test.

The canonical `tests/run_tests.py` harness now checks `[SILENT]`, fail-closed holds and durable supervisor capacity/deduplication instead of the removed gateway `FIRE` contract.

## Unattended fixer push policy (host operator; not GitHub owner consent)

An installed config defaults `unattended_fixer_push` to `false`, including legacy files. Neither init, plugin settings, apply, route events nor sandbox requests opt a repository in. The explicit `hermes review-loop fixer-push --loop ID --enable --acknowledge-pr-race` command changes one host config after warning about the accepted non-atomic PR-metadata/ref race; `--disable` reverses it. The CLI caller controls local host config: this is **host-operator opt-in**, not proof of GitHub owner/admin authorization. In particular, a personal-account collaborator cannot be assumed to have admin permission. No live repository has been opted in by this patch.

At broker push time, the host reloads the repository config; absent, invalid, duplicate, or disabled permission denies before Git. Loop ID and exact config filename must match the launch snapshot; symlinked config files are refused. The host CLI serializes explicit policy changes with the broker's final reload and entire ref operation, so a successful CLI disable returns only after any already-authorized push finishes. Set/apply snapshots and rollback preserve the latest policy bit under that lock; enabling checks the supervisor ledger as well as gate state for in-flight fixer runs. Production fixer enqueue serializes against the same policy lock and records `push_admitted` in the run ledger: a disabled or legacy run cannot borrow a later enable, while a later disable still revokes permission at the broker write boundary. Direct/manual config edits do not use this lock and are not covered by that serialization guarantee; disable with the CLI and inspect active runs. The per-run socket binds repo/PR/head/branch/fixer seat and consumes one push attempt before the write; exact PR eligibility and ref identity are rechecked around the exact-SHA lease. Before calling the external push path, the broker commits a host-ledger push intent; refusal prevents the Git call. The intent is a PR-wide hold even if later quarantine persistence fails or the worker exits, and duplicate/replayed attempts are refused. Only a successful exact ref/PR readback and durably committed completion clears it; failure to commit completion remains held for operator reconciliation. An unknown ref update or a published ref with unverifiable PR state quarantines the supervisor seat, suppresses review/merge handoff, and queues an operator notice; it is not retried automatically. The notice outbox is not an acknowledged user delivery channel. A close/reopen entirely between final PR check and readback remains unobservable, even when the ref lease succeeds. Merging code does not enable the host config or arm a production route; the security review and delivery/live gates above remain open.

Do not enable the route in production or close #16 based on offline tests alone.
